# Decision Record

Decisions that are settled. Each names what it rules out, because several of
these were made by rejecting a proposal that looked reasonable — and the
rejected version is the one that comes back if only the conclusion is written
down.

The [constitution](constitution.md) holds principles; this file holds choices
made under them. Where a decision tightens or interprets a principle, it says
which one. Open questions are at the bottom, not mixed in.

**Last updated:** 2026-08-23.

---

## D1 · filesnap is a hard copy of the codex engine, with no path back

The engine was written inside a fork of OpenAI Codex and copied out on
2026-08-22. codex keeps its own inlined copy, untouched. The two share no code
path and never will.

**Rules out:** git subtree, vendoring, a shared crates.io dependency, or any
sync script in either direction. A defect found in one that also exists in the
other is *reported*, not ported — porting is a deliberate act with its own
review, never a sync.

**Why:** an argument for a single source of truth was made and rejected. The
fork's constraints (upstream merges, Bazel, the RFC's "self-contained workspace
member" pitch) and this project's constraints (a published, independently
versioned library) pull in opposite directions, and every mechanism that serves
both adds a permanent obligation to both. The cost of divergence is known and
accepted.

## D2 · Two repositories, and the plugin gets its own

`filesnapshot` holds the Rust workspace: the engine crate, the CLI, and the npm
packaging. The DeepSeek Harness plugin gets a **separate repository**, created
at first publish.

**Rules out:** one monorepo holding all three; and equally, three repositories.

**Why:** the CLI and the plugin ship in lockstep — the plugin spawns the CLI
binary and speaks its protocol — so splitting those two buys a cross-repo
release dance for nothing. But every published dsh plugin is one-package,
one-repository, and the repository *is* the landing page: stars, issues, and
the npm link all land there. A plugin living in a subdirectory of a Rust
monorepo shows a visitor `crates/` and `Cargo.toml` first. Creating the plugin
repo at publish time costs no visibility, because nobody has seen it before
then.

## D3 · The CLI is stateless per invocation

Every invocation is a new process. All state that must survive between
invocations lives on disk.

**Consequence, not yet resolved:** the edit-touched partition is held in memory
by `SnapshotTracker` and is lost when the process exits, so a sidecar sees it
empty on every call. See O1.

## D4 · A session is bound to one working directory, permanently

A `session_id`, once bound to a working directory, may never be used against a
different one. The binding is recorded and enforced by the caller; the engine
does not know about it.

**Why this over character validation:** manifest keys are **absolute paths**.
Running a session captured under `/a` while the user is in `/b` does not corrupt
`/b` — it silently operates on `/a`. Action at a distance, with no error. That
is a worse failure than two sessions colliding onto one log, and validating the
id's characters does not prevent it at all.

## D5 · No path may escape the store boundary, absolute or relative

Every id that becomes a filename must be proven incapable of resolving outside
its directory. Today `/` is mapped to `_`, so `../../etc/passwd` cannot
traverse — but `..`, `.`, and the empty string survive sanitizing and resolve to
the directory itself.

**Also to be fixed here:** files under `turns/` have no extension, so
`write_atomic`'s `path.with_extension("tmp")` truncates at the last dot —
`turns/v1.2` and `turns/v1.9` share the temporary path `turns/v1.tmp`. Turn ids
are external conversation ids and dots in them are ordinary. Giving those files
an extension fixes the collision and makes a whitelist possible (see D9).

## D6 · Turn ids come from outside and are never generated by us

A `turn_id` is the join key to an external conversation. The engine and the CLI
take it as given.

**Rules out:** the CLI minting its own turn ids. That was proposed and rejected:
minting one severs the join, which is the only thing the id is for.

**Ordering is a separate mechanism.** "Go back N steps" needs an order, not an
id, so ordering comes from a timestamp or an internal hash chain in the git
style — **linear history only, no branches**. The order is what N counts.

**Watch out:** a session's log holds several entries per turn (one scan plus any
pre-edit attaches), so N must be counted over distinct turns, not over log
entries.

## D7 · Ids are validated by rejection and namespaced by prefix

Invalid ids are refused, not silently rewritten. User-supplied ids and
internally minted ones live in disjoint prefixes.

**Why:** `safe_file_name` maps every character outside `[A-Za-z0-9._-]` to `_`,
so `my session`, `my/session` and `my:session` all become `my_session` — three
distinct sessions merging into one log and one undo stack. Silent rewriting is
what turns a typo into a collision. Separately, the engine mints turn ids as
`safety-restore:<id>`, which sanitizes to `safety-restore_<id>`; a user turn of
that name collides exactly. Prefixes make the two namespaces disjoint by
construction rather than by luck.

## D8 · `gc` is exclusively an orphan and cache collector

It reclaims orphaned records and unreferenced bytes. It has no other function
and no session semantics.

**Testable contract:** running gc, or not running it, any number of times, never
changes what any session can rewind to. Every turn resolves to the same manifest
before and after.

## D9 · `delete` is the single source of truth, and has no preconditions

Explicit delete is the only mechanism that ends a session's data. Its
correctness must not depend on gc having run, on the absence of residue, or on
anything else being true first.

**Rules out:** the proposal that delete sweep `.tmp` residue first. That is a
precondition, and a precondition is exactly what stops delete being
authoritative.

**The fix is structural instead:** make `.tmp` incapable of being read as a
record anywhere, by whitelisting the expected shape in every enumeration.
`blobs/` and `manifests/` and `refs/` already do this (two different mechanisms
— a `.tmp` blacklist and a `.json` whitelist — which will drift; unify on
whitelist). `turns/` and `restores/` do neither, which is why residue there
becomes a permanent false GC root. Once residue is not data, delete is correct
whatever is on disk, and gc reclaims the residue as dead bytes.

**Second precondition, also to be removed:** `forget_sessions` reads each
session's log inside `if let Ok(...)` and deletes the log regardless. A corrupt
or unreadable log therefore means nothing enters the doomed set while the record
that would let you retry is destroyed — delete reports success and reclaims
nothing. A read failure must refuse that session and say so, leaving it intact.
This makes the void return type wrong: delete must report what it reclaimed and
what it refused.

## D10 · `delete` and `gc` are independent, with clear boundaries

| | owns |
|---|---|
| `delete` | records keyed by session id: the session's log, its undo records, and the turn entries whose turn ids no surviving log holds |
| `gc` | `.tmp` residue past the grace window, and anything unreachable |
| **neither** | **content.** Manifests and blobs are reclaimed by reachability, by both, through one shared read-only query |

Neither may depend on the other's contract. **Sharing a low-level primitive is
not a dependency; depending on the other operation's contract is.**

**Content cannot be owned, and an earlier version of this table said it could.**
Manifests and blobs are content-addressed and deduplicated: `ManifestStore::save`
and `BlobStore::store_bytes` both write nothing when the hash is already present.
Two unrelated sessions that capture identical state therefore share the same
manifest id and the same blobs — sharing follows from *content*, not from
lineage, so no session can be said to own any of it. "Delete the manifests only
this session referenced" is not answerable except by a global reachability query.
That coupling is inherent to a deduplicating store, not an accidental
entanglement, and severing it would trade a disk leak for `MissingBlob` in a
session nobody deleted.

**Where the code violates this today — one weld, not two:**
`forget_sessions` → `gc_for` → `collect_garbage_for` → `live_manifest_ids`,
which is a *query that writes*: it answers "who is still live" and, as a side
effect, prunes the turn index. So delete's own record cleanup happens inside
gc's marking helper, and delete's result depends on what gc's marking logic
read. That same helper is where unwhitelisted `.tmp` files enter delete's
liveness computation (D9) — one hole, two symptoms.

**Fix shape:** split it into a pure read-only `live_manifests(refs)` that both
call, plus explicit pruning that each operation performs for the records it
owns. Note this does not make delete self-sufficient for content — see above —
it makes the *query* shared rather than one operation reaching through the
other's entry point.

**A full entanglement audit (2026-08-23) confirmed six defects on this
boundary**, recorded as C12–C15 in [compliance.md](compliance.md) plus
sharpened C4 and C5. The two that bear directly on this decision:

- `retain_turns`, reached from delete, unlinks turn entries **by global
  elimination** rather than scoped to the sessions being deleted, so deleting
  one conversation can amputate another's history (C12). This is the exact
  shape D10 forbids.
- `collect_garbage_for` removes the doomed manifests *before* resolving which
  blobs survive, so a failure in between orphans blobs that no later delete can
  ever rediscover — an invariant only the other operation could restore (C13).

## Open

- **O1 · How the edit-touched partition survives a process boundary.** Three
  candidates: persist it as its own append-only file; rehydrate the whole key
  set from the latest manifest (imprecise — carries the git and recency
  partitions too, so tracking then only grows, at up to 100 paths per
  invocation); or diff manifests per turn (exact but reads two manifests per
  turn). The first is preferred: of the three partitions only the edit-touched
  one is *history* — the other two are recomputed every capture, and storing
  them would resurrect stale data rather than remember anything.
- **O2 · Serializing concurrent restores.** The capture path deliberately takes
  no lock. A library inside one long-lived process serialized restores by
  construction; a CLI does not. Either the interface prevents two concurrent
  restores into one directory or it takes a real lock with owner identity and
  stale recovery. Named as unsettled in the constitution.
- **O3 · The CLI command surface and the sidecar protocol.**
- **O4 · C1 and C2 land together.** Both change the manifest, and adding a field
  re-identifies every record on disk, so they are one change or none.
- **O5 · Whether the crate keeps the name `filesnap`.** Free on crates.io and
  npm; the counter-argument is that the code spells `file_snapshots` everywhere.
  Nearly free to change until the first publish.
